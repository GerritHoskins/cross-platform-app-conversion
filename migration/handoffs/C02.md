## Design choices (in gaps the contract does not spell out — all strict)
- Validation order (deterministic): (root) → schedule → schedule[0] → schedule[0].date → schedule[0].groups → speakers[] → tracks[] → groups and sessions in document order.
- Top-level speakers and tracks are treated as required arrays (the fixed interface demands them; strictness principle).
- location: any string, empty allowed (only name is explicitly required non-empty).
- Empty session tracks array is allowed by the rules; the fixture has zero such sessions (verified via node -e probe).
- Fixture facts (node -e probes): 8 groups, 20 sessions, ids 1-20, 8 distinct groupTimes (8:00 am … 3:00 pm), 10 top-level tracks, 13 speakers, 19/20 sessions have description, 18/20 have speakerNames, all speakerNames resolve (no unresolved names), session 1 has no description and no speakerNames, no session has an empty tracks array.
- Duplicate speaker names: later entry wins (Map semantics, matching the source store's `new Map(speakers.map(...))`).
- Duplicate session id: ConferenceDataError raised at the second occurrence's .id path.
- Unparseable session/group start or end times are rejected (startMinutes/endMinutes always finite); compareTimes additionally handles Infinity/NaN defensively, exactly as the reference implementation.
- Purity: output objects and arrays are always freshly created; no input mutation and no shared arrays across repeated normalizations (tested).
