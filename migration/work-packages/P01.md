2. Write `migration/reference/derive-expected.mjs`: a dependency-free Node ES module that reads `public/data/data.json` and transcribes the source logic, with a comment citing file and line for each function:
   - normalization from `loadSessionData` (numeric IDs, `description || ''`, `groupTime` from the group, speaker IDs by name),
   - first-load track selection (every track that appears on a session),
   - `allFiltered` / `favoritesFiltered` (every session track must be selected; no selected tracks gives no sessions; case-insensitive name `includes` search),
   - `groupedByStartTime`, sorting with the same 12-hour parsing as `src/utils/time.ts` (malformed times sort last, equal times keep input order),
   - `addFavorite` (no duplicates) and `removeFavorite` (absent ID is a no-op).
   It writes `migration/reference/expected-cases.json` and prints a one-line summary. Run with `node migration/reference/derive-expected.mjs` from the repository root.
3. The JSON has `sourceDataSha256`, `normalizedSessionCount`, and a `cases` array. Each case has `id`, `description`, `input` (`searchText`, `selectedTracks`, `favoriteIds`, `mode`), and `expected` (`sessionIds` in display order, `groups` as `[{ groupTime, sessionIds }]`). Include at least:
   - `default-all`: first-load tracks, empty search, mode `all`
   - `no-tracks`: empty `selectedTracks`
   - `single-track`: one track only (pick one where multi-track sessions are excluded, to show the "every track" rule)
   - `search-case-insensitive`: mixed-case substring that matches more than one session
   - `search-no-match`
   - `search-plus-track`: search and a track subset together
   - `favorites-empty`: mode `favorites`, no favorites
   - `favorites-some`: two favorites, one excluded by track filter
   - `favorites-order`: favorites added in reverse time order still display chronologically
   - `add-duplicate` and `remove-absent` favorite list cases (`expected.favoriteIds`)
4. Write `migration/reference/contract.md` with these sections and keep each claim tagged `[static]` (read in code), `[derived]` (produced by the script), or `[unverified]` (needs a running app):
   - Data and normalization: fields, defaults, unresolved speaker handling (source maps to `undefined`; contract says omit), session without description, time format.
   - Selection rules: the filter and search semantics above, and that the filter modal starts with all tracks checked on first load.
   - Grouping and ordering: section headings come from group time; order within and across sections; equal-time ordering kept stable.
   - Favorites UI: list "Favorite" action adds immediately and then shows a "Favorite Added" alert; adding an existing favorite opens the remove-confirmation alert instead; list "Remove" asks for confirmation and Cancel keeps it; detail star toggles immediately with no alert.
   - Filter modal: draft selection, Select All / Deselect All, Apply replaces the filter, Cancel/dismiss keeps the old filter.
   - Navigation: detail route `/tabs/schedule/session/:sessionId`; cold entry loads data first; unknown ID leaves `session` undefined (record what the template then renders as `[static]` or `[unverified]`).
   - Speaker-session entry (deferred): the speakers tab opens the same detail view at `/tabs/speakers/session/:sessionId`. Record this route and its back target, but write no expected cases for it. Slice 1 targets reach detail only from the schedule; their detail screen must take a session ID and not assume the schedule is its parent, so the speakers entry can be added later without rework.
   - Fixed before P01 (record as `[static]` history, not open defects): schedule and `conferenceStart` sorting used engine-dependent `Date` parsing and now use `src/utils/time.ts`; the filter modal no longer clears `isFirstLoad`, so the store is its only writer.
