## State contract additions

In `conference-state.tsx`:

- Extend `ConferenceAction` with `{ type: 'favoriteAdded'; sessionId: number }` and `{ type: 'favoriteRemoved'; sessionId: number }`. The reducer applies public core `addFavorite`/`removeFavorite` to the current `selection.favoriteIds` inside the reducer, so rapid consecutive dispatches compose correctly; do not compute the new list in components from a captured render value. Duplicate add and absent remove leave the favorite IDs equal (core semantics). Before a selection exists both are no-ops. Other fields survive; the reducer stays pure and immutable.
- Export `selectSessionById(state, sessionId: number): Session | undefined` — `undefined` unless ready with a conference.
- Export `selectIsFavorite(state, sessionId: number): boolean` — `false` without a selection.
- `setFavoriteIds` remains for fixture-driven tests; product UI uses the two new actions.

## Navigation contract

- Route: `src/app/session/[sessionId].tsx` reads `sessionId` with `useLocalSearchParams`, normalizes an array value to its first element (missing → empty string) and renders `<SessionDetailScreen sessionId={value} />`. No other logic in the route file.
- `SessionDetailScreen({ sessionId }: { sessionId: string })` takes only the raw ID string. It must not import the schedule screen, read navigation history or assume the schedule is its parent, so the deferred speakers entry (`contract.md` Speaker-session entry) can reuse it.
- ID resolution: an ID is valid only when it is a string of ASCII decimal digits whose numeric value matches a loaded session. Anything else (`abc`, `3abc`, `-1`, empty, an unmatched number) is unknown. **Decision:** this is stricter than the source's `parseInt` (which would accept `3abc` as 3); the contract marks unknown-ID behavior unverified, so record the decision in the handoff.
- `_layout.tsx`: register `<Stack.Screen name="session/[sessionId]" options={{ title: 'Session' }} />` after the index screen and export `unstable_settings = { initialRouteName: 'index' }`, so a cold deep link to a session still has the schedule beneath it and back lands on the schedule (source `defaultHref = "/tabs/schedule"`). Keep the existing index options. The source nests the schedule stack inside tabs; tabs arrive with the deferred speakers work, so the single Stack is the schedule stack for slice 1. State this in the handoff rather than adding tabs.
- Back from detail pops to the same mounted schedule screen: search text, mode, favorites and scroll position are retained, and the loader is not called again.

## Detail UI contract

- Idle/loading: `Loading session…` with progress semantics. Error: `Unable to load sessions.`, the captured message and a labeled `Retry` that calls the provider's retry. Never show "not found" before data is ready.
- Ready, known session: accessible heading with the session name; track names; description (omit the paragraph when empty); original `timeStart – timeEnd`; location.
- Ready, unknown ID: visible `Session not found.`; no session content. The favorite toggle stays visible but is disabled and dispatches nothing (source: `isFavorite` is false and `toggleFavorite` returns early).
- Favorite toggle: an in-screen accessible button (not a header slot, to stay independent of the navigator) with label `Add to favorites` when not favorite and `Remove from favorites` when favorite, plus `accessibilityState.selected` equal to the favorite state. Pressing it dispatches `favoriteAdded`/`favoriteRemoved` immediately, with **no alert** (`contract.md` Favorites UI, detail star).
- Placeholders: render a Share button and the five source actions (`Watch`, `Add to Calendar`, `Mark as Unwatched`, `Download Video`, `Leave Feedback`) with no handlers and disabled accessibility state. Do not implement sharing, calendar, video or feedback.
- Native layout, readable light/dark colors via the existing theme approach, scrollable content, no HTML/DOM APIs.

## Schedule list additions

- Each row's content becomes one pressable with `accessibilityRole="link"`, label = session name, that pushes `/session/<id>` via expo-router. Keep testID `session-<id>` on the row container and the existing row text.
- Each row has a separate sibling button (never nested inside the link pressable, so pressing it cannot navigate): in all mode labeled `Favorite <session name>` with visible text `Favorite`; in favorites mode labeled `Remove <session name>` with visible text `Remove`.
- All-mode Favorite, session **not** a favorite: dispatch `favoriteAdded` first, then `Alert.alert('Favorite Added', undefined, [{ text: 'OK' }])`. The favorite exists even if the alert is never dismissed.
- All-mode Favorite, session **already** a favorite: **decision (human, 2026-10-25): reproduce the source quirk** (`contract.md` Known source defects, `SessionList.vue:305-325`). Show the removal confirmation `Alert.alert('Favorite already added', 'Would you like to remove this session from your favorites?', [Cancel, Remove])`. Cancel dispatches nothing; Remove dispatches `favoriteRemoved`. Record it in the handoff as a deliberate reproduction, not a new defect.
- Favorites-mode Remove: same confirmation with title `Remove Favorite`; Cancel keeps the favorite, Remove dispatches `favoriteRemoved` and the row leaves the favorites list.
- Use `style: 'cancel'` for Cancel and `style: 'destructive'` for Remove. No custom modal, toast or snackbar. Rows show no star state; favorite state is visible through the favorites mode and the detail toggle.
