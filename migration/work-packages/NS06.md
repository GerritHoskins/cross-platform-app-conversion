## Outcome and boundaries

Add a horizontal swipe on each schedule row that reveals the same favorite action as the row's existing button, reusing the NS04 handler and dialogs. This is the NativeScript counterpart of RN06, with the same business cases: the revealed action is `Favorite` in all mode and `Remove` in favorites mode; pressing it behaves exactly like the button (add-then-inform, the already-favorite quirk, remove-with-confirmation); the row closes when the dialog is answered; one row is open at a time; tapping an open row closes it instead of navigating; vertical scrolling still works; the visible buttons stay as the accessible path. The plan forbids an unreviewed plugin fallback, so the swipe uses NativeScript core gestures only. No dependency changes. Full Android acceptance (hardware Back, keyboard, large text, dark mode, RN07-style F01–F05) stays in NS07.

## Decisions to answer (human)

- **D1 — gesture mechanism.** Recommended: core `swipe` gesture on the row content. A leftward swipe opens the row (reveals the action); a rightward swipe on an open row closes it; up/down swipes are ignored so the ListView keeps vertical scrolling. The reveal is a fixed offset bound to state (no finger-following drag). Simple, recycling-safe, testable as pure state. Alternative: `pan` with the content following the finger and a 40 dp open threshold — closer to Ionic's sliding feel, but a stateful per-view drag that interacts with ListView recycling and vertical scroll; not recommended for this slice.
- **D2 — reveal structure.** Recommended: inside the existing column 0, two layers in one cell: behind, a `Button` action panel aligned right, width 96, `minHeight` 48, text `Favorite` (all mode) / `Remove` (favorites mode), `automationText` `swipe-action-<id>`, `accessibilityHidden` true (the visible column 1 button remains the accessible path, so each action is announced once); in front, the existing row content with an opaque background and `translateX` bound to `openId === session.id ? -96 : 0`. Keep `session-<id>`, the column 1 button and every NS04 text unchanged.
- **D3 — action reuse and closing.** Recommended: the swipe action calls the same `changeFavorite(id)` as the button (no second favorite implementation); the swipe path closes the row after `changeFavorite` resolves, i.e. when OK, Cancel or Remove is pressed (source parity: the sliding item closes from the alert buttons). The button path is unchanged. Dispatch order and dialog text must not change.
- **D4 — open-row state.** Recommended: NEW pure `src/state/row-swipe.ts` (no NativeScript imports): `RowSwipeState = { openId: number | null }` and `rowSwipeReducer(state, event)` for `swipe-left(id)` (opens `id`, closing any other: single-open), `swipe-right(id)` (closes if `id` is open), `settled(id)` (closes if open), `list-changed` (closes any). Plus `rowTapAction(state, id)`: `'close'` when that row is open (no navigation — link guard), else `'navigate'`. `Schedule.vue` keeps the state in a `ref`, dispatches `list-changed` from a watcher on search text, mode and selected tracks (not favorites: a favorite change comes from `changeFavorite`, which closes through `settled`), and routes row taps through `rowTapAction`.
- **D5 — tests.** Recommended: Vitest only. Reducer table: open, single-open replacement, right-swipe close (and no-op on a closed row), settled close, list-changed close, immutability of the input state; `rowTapAction` for open/closed/other rows; that the swipe path uses `listFavoriteAction` unchanged (the action label helper `swipeActionLabel(mode)` returns `Favorite`/`Remove`, matching `listFavoriteAction`'s branches). Gesture activation, the reveal, the dialogs through the swipe path and vertical-scroll coexistence are device evidence only (disclosed, as NS03–NS05). Keep all 94 NS05 tests.
- **D6 — device observation.** Recommended: rebuild, `adb install -r`, verify the installed hash, cold launch, then PNG + UI XML at each step (taps only at bounds from the current XML; no text input; no hardware keys — ActionBar back only). Horizontal reveal: `input swipe <content right − 40> <row centre y> <content right − 400> <same y> 300` inside the row content; vertical scroll: `input swipe 540 1800 540 900 400` inside the ListView. Record every gesture's coordinates.
  1. Baseline schedule (All sessions, all tracks).
  2. Swipe left on a non-favorite row → `Favorite` action revealed; tap it → `Favorite Added`; OK → row closed; the session is listed under Favorite sessions.
  3. Back in All: swipe the same row → `Favorite`; tap → `Favorite already added`; Cancel → row closed, still a favorite.
  4. Favorite sessions: swipe → `Remove`; tap → `Remove Favorite`; Remove → `No favorite sessions.`
  5. Vertical drag across rows: the list scrolls, no row opens, no navigation (before/after frames).
  6. Open a row; tap its content → the row closes and no detail opens; tap it again → detail opens; ActionBar back.
  7. Open row A, then swipe row B → A closed, B open.
  8. Open a row; switch mode → the row is closed after the switch (list-changed); apply a one-track filter through the NS05 modal → any open row closed and the filter applied.
  9. The visible `Favorite`/`Remove` buttons remain present and labelled throughout.
  Alternative: also send hardware Back while a row is open — not recommended (NS07 owns hardware Back).

## Amendment A1 (human-approved 2026-10-27, after phase B run 1)

Phase B run 1 (`migration/evidence/NS06/b-device/`, `migration/handoffs/NS06-checkpoint-b.md`) recorded FAIL: no prescribed reveal opened a row. The coordinator's pixel inspection found the cause, which the UI XML could not show: on Android the swipe-action `Button` (elevated by the platform's button style) is drawn above the opaque row content although it is the earlier child, so every row permanently shows a second `Favorite` button in the right part of column 0. The reveal gestures started at `content right − 40` (x = 767 px), inside that button, which consumed the touch, so the content's `swipe` handler never received it. Because the action is `accessibilityHidden`, it is absent from the UI XML; only the pixels show it.

The human approved:
1. D2 changes only in this respect: the swipe-action `Button` is rendered only while its row is open (`visibility` `visible` when `openId === session.id`, otherwise `collapse`). Everything else in D1–D6 is unchanged (96-wide right-aligned action, `swipe-action-<id>`, `accessibilityHidden`, content `translateX` −96 when open, reuse of `changeFavorite`, settle-close, pure reducer, list-changed close, link guard).
2. Because the hidden action is not in the UI XML, phase B taps it at the computed centre of the revealed strip: x = midpoint between the open content's right edge (from XML) and its closed right edge, y = the row content's vertical centre; the computation is recorded with every tap.
3. Rerun as phase A run 2 (fix and full gates; evidence `a-gates2/`, checkpoint `NS06-checkpoint-a2.md`) and phase B run 2 (evidence `b-device2/`, checkpoint `NS06-checkpoint-b2.md`). Run 1 records stay as immutable history; the coordinator's pixel inspection covers both runs.

Open risk, to be shown by phase B run 2 rather than assumed: whether the ListView re-renders recycled cells when `openId` changes.

## Coordinator correction C1 (2026-10-27, after phase B run 2; no scope change)

Phase B run 2 (`migration/evidence/NS06/b-device2/`, `migration/handoffs/NS06-checkpoint-b2.md`) observed every reveal moving the row content's right edge left by exactly 96 dp (252 px), and the coordinator's pixels (`b-device2/B2-open.png`) show the content slid left with the `Favorite` action filling the revealed strip — so A1 works and the ListView re-renders on `openId`. The run nevertheless recorded the swipe-dependent steps BLOCKED because the coordinator's prompt defined "open" as both edges shifting; the content starts at x = 0 and uiautomator clips bounds to the screen, so the left edge can never show the shift. The coordinator corrects the rule: a row is open when its `session-<id>` content's right edge is at least 240 px (≈ 96 dp at density 420) left of its closed right edge, and closed when it is within 10 px of it; the left edge is recorded but not asserted. Everything else, including the A1 tap rule, is unchanged. Phase B run 3 writes `b-device3/` and `NS06-checkpoint-b3.md`; runs 1 and 2 stay as history.
