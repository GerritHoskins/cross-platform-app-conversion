## Data and normalization

- `data.json` structure: `schedule[0].groups[]`, each group a `{ time, sessions[] }`; each session `{ id, name, timeStart, timeEnd, location, tracks[] }` plus optional `description` and `speakerNames[]`; top-level `tracks[]` and `speakers[]`. [static] `public/data/data.json` structure; normalization at `src/store/modules/sessions.ts:102-121`.
- **8 groups** from "8:00 am" through "3:00 pm"; **20 sessions** total, IDs `1`-`20`; **10 track names**; **13 speakers**. [derived; script output over `public/data/data.json` (its sha256 is at `expected-cases.json:2`); the 8-group display order is `default-all.groups` at `expected-cases.json:48-108`]
- IDs are strings in the data (`"1"`, `"2"`, ...) and become numbers in the store via `parseInt(session.id)`; the script transcribes the same conversion. [static] `src/store/modules/sessions.ts:109`.
- `description` defaults to `''` via `session.description || ''`. [static] `src/store/modules/sessions.ts:114`. Session 1 ("Breakfast") has no `description` in the data, so its normalized description is `''`; it is the only session of the 20 without one. [derived] script over `data.json`.
- `groupTime` is copied from the group's `time`; it is never derived from session times. [static] `src/store/modules/sessions.ts:118`.
- Session times are 12-hour strings such as `"8:00 am"`, `"10:15 am"`, `"1:00 pm"`. [static] time pattern at `src/utils/time.ts:1`; data format in `public/data/data.json`.
- `speakerIds` are resolved by a `name -> parseInt(speaker.id)` map built from `speakers[]`; every name in this fixture resolves to an ID. [static] `src/store/modules/sessions.ts:103-105,115`. [derived] script over `data.json` (0 unresolved names).
- **Contract decision (unresolved speakers):** the source maps an unknown `speakerNames` entry to `undefined` inside `speakerIds` (`src/store/modules/sessions.ts:115`). The contract for migration targets is that such entries are **omitted** from `speakerIds` rather than emitted as `undefined`. This is a deliberate policy, not observed source output; the fixture does not exercise it because all names resolve. [static] observed behavior; policy is a decision of this contract.
- **Contract decision (time parsing):** order comparisons must use the explicit 12-hour parse in `src/utils/time.ts` (pattern `^\s*(\d{1,2}):(\d{2})\s*(am|pm)\s*$/i`; hours 1-12, minutes 0-59; `12:xx am` = 00:xx; `12:xx pm` = 12:xx; unparseable input -> `Infinity`, i.e. sorted last), never engine-dependent `Date` parsing. `compareTimes` returns `0` when the difference is `NaN` (both operands unparseable), so such pairs keep input order. [static] `src/utils/time.ts:1-23`; this is a fixed rule for the reference and for core/targets, recorded as a deliberate substitution rather than observed app output.

## Selection rules

- "All" mode uses `allFiltered`; "Favorites" mode uses `favoritesFiltered`; the segment control selects which getter feeds the list. [static] `src/views/SessionList.vue:293-298` (computed at 293-298, segment at 256, template segments at 9-12 and 39-42).
- `allFiltered`: if `trackFilters` is empty, **no** sessions pass; otherwise a session passes only if **every** one of its tracks is in `trackFilters`; the optional search is a case-insensitive `includes` of the lowercased query in the lowercased **name** (name only, not description or location). [static] `src/store/modules/sessions.ts:192-206`.
- **Fixture limitation + supplemental check.** Every real session in the fixture is single-track, so the every-track inclusion rule (include a session only if **all** of its tracks are selected) is not exercised by any source-derived case (all 20 real sessions carry exactly one track). To still catch an `any`-vs-`every` regression, `derive-expected.mjs` runs a dependency-free **supplemental** self-check — explicitly labeled *synthetic, not fixture*: a two-track session is **excluded** when only one of its tracks is selected and **included** when both are, asserted for **both** `allFiltered` and `favoritesFiltered` before the fixture is written (see the supplemental block in `derive-expected.mjs`). This check defends against a `some`-based implementation but is **not** one of the fixture cases. [derived; supplemental, not a fixture case]
- `favoritesFiltered`: first requires the session to be in `favoriteSessions`; then applies the same empty-filter, every-track, and search rules. [static] `src/store/modules/sessions.ts:208-224`.
- Favorite list is order-sensitive: `addFavorite` appends (no duplicates), `removeFavorite` filters. [static] `src/store/modules/sessions.ts:72-79`; actions at `src/store/modules/sessions.ts:161-166`.
- First load: `state.isFirstLoad` starts `true`; when session data loads and the flag is set, `trackFilters` is initialized to **every track that appears on a session**, in first-appearance order, via `new Set(sessions.flatMap(s => s.tracks))`. [static] `src/store/modules/sessions.ts:42,124-128`. For this fixture that order is `Food, Ionic, Tooling, Vue, Design, Services, Workshop, Communication, Navigation, Documentation`. [derived] script over `data.json`.
- The track-filter modal starts with **all tracks checked on first load** (reads `store.state.sessions.isFirstLoad` and checks every available track while it is true); afterwards it mirrors the current `trackFilters`. [static] `src/views/SessionListFilter.vue:141-151`.
- `updateTrackFilters` **replaces** the whole filter; `addTrackFilter`/`removeTrackFilter` adjust it incrementally (incremental mutations are committed nowhere in the slice-1 UI). [static] `src/store/modules/sessions.ts:58-68`.
- Search text lives in the store (`setSearchText` dispatch from the searchbar `ionInput`); empty string disables the search clause. [static] `src/views/SessionList.vue:16-22,378-380`.

## Grouping and ordering

- The visible list is `groupedByStartTime(getterPool)`: copy, **stable-sort by `timeStart`** using `compareTimes`, then group by `groupTime` in first-occurrence order; each group keeps a `startTime` heading (the data's group time) and its `sessions` in sorted order. [static] `src/views/SessionList.vue:269-291`.
- Group headings are the group times from the data (`"8:00 am"`, ..., `"3:00 pm"`), not computed values. [static] `src/store/modules/sessions.ts:118`; `src/views/SessionList.vue:285-291`.
- Section order is first-occurrence order after the time sort. With the full fixture this yields the chronological order `8:00 am, 9:15 am, 10:00 am, 11:00 am, 12:00 pm, 1:00 pm, 2:00 pm, 3:00 pm`. [derived] `default-all` case in `expected-cases.json`.
- Within a section, sessions are ordered by `timeStart`. Where two sessions share a start time (fixture: sessions 6 and 7 at `10:15 am`; sessions 10 and 11 at `11:30 am`) they keep input order, relying on stable sort. [static] sort at `src/views/SessionList.vue:270-272`; stability via the contract decision in the Data section. [derived] `default-all` case.
- The visible groups come from a mode-aware `allGrouped` computed (all-mode pool from `allFiltered`; favorites-mode pool from `favoritesFiltered`) plus a reactive `watch` on `store.getters.allFiltered`. **Caveat:** that `allFiltered` watch (at `SessionList.vue:405-410`) unconditionally writes `allGroupedRef`, so in favorites mode a search change can surface non-favorite sessions — a known open source defect, not the intended getter-level contract (recorded under Known source defects). [static] `src/views/SessionList.vue:261-263,293-298,405-410`.
- The derivation script `derive-expected.mjs` transcribes exactly these steps (allFiltered at `derive-expected.mjs:100-110`, favoritesFiltered at `derive-expected.mjs:114-125`) and produces the expected pools (11 cases at `expected-cases.json:4-516`); the flat `expected.sessionIds` list equals the flatten of `expected.groups`, enforced by a hard invariant loop at `derive-expected.mjs:292-309` that exits non-zero on any disagreement. ## Favorites UI

- List "Favorite" action (all-mode row, sliding option): if the session is **already** a favorite, the code does **not** add it; it opens the remove-confirmation alert titled "Favorite already added". Otherwise it dispatches `addFavorite` **immediately** (before the alert) and then presents a "Favorite Added" alert whose single OK button closes the sliding item. [static] `src/views/SessionList.vue:82-88,305-325`.
- List "Remove" action (favorites-mode row): presents a confirmation alert ("Would you like to remove this session from your favorites?"); **Cancel** closes the sliding item without dispatching anything (favorite kept); **Remove** dispatches `removeFavorite` and closes the sliding item. [static] `src/views/SessionList.vue:90-98,327-351`.
- Detail star: `toggleFavorite` dispatches `removeFavorite` or `addFavorite` **immediately, with no alert**; the star icon reflects `isFavorite`, which is `favoriteSessions.includes(session.id)` and returns `false` when `session` is undefined. [static] `src/views/SessionDetail.vue:9-11,183-196`.
- The store mutations are pure state operations: `addFavorite` no-ops on duplicates; `removeFavorite` no-ops for absent IDs. [static] `src/store/modules/sessions.ts:72-79`.
- The two list actions therefore have the immediate-then-confirm semantics: add fires first (alert is informational), remove requires confirmation. [static] `src/views/SessionList.vue:305-351`.
- Alert wording, slide-gesture feel, and button layout have not been observed in a running app. [unverified]

## Known source defects and quirks (still open; not fixed in the reference)

- `data.json` is fetched **twice**: `loadSessionData` and `fetchTracks` each read the same file. [static] `src/store/modules/sessions.ts:91-131,134-148`.
- Unresolved `speakerNames` are mapped to `undefined` inside `speakerIds` (not omitted) in the current source. [static] `src/store/modules/sessions.ts:115`.
- `addTrackFilter` is a mutation that nothing in the slice-1 UI commits (only `updateTrackFilters` is dispatched). [static] `src/store/modules/sessions.ts:58-62`; dispatch sites at `src/views/SessionList.vue:365-369`.
- The list "Favorite" action, once a session is already favorited, routes into the remove-confirmation branch instead of reporting "already added" as an add; the add path is bypassed. [static] `src/views/SessionList.vue:305-325`.
- `openSocial` shows a fake loading ("Posting to <network>") with a random duration and does not post anywhere. [static] `src/views/SessionList.vue:111-120,382-389`.
- The `queryText` ref bound to the searchbar `v-model` is separate from the `store.searchText` used by `updateSearchTerm`; the two can diverge. [static] `src/views/SessionList.vue:16-22,257,378-380`.
- `checkAndLoadData` only reloads if `allGroupedRef` is empty; it dispatches `loadSessionData`, `loadSpeakerData`, and `fetchTracks` together. [static] `src/views/SessionList.vue:391-397`.
- **Competing watchers overwrite the shown groups in favorites mode.** `src/views/SessionList.vue:405-410` registers a `watch` on `store.getters.allFiltered` whose handler unconditionally reassigns `allGroupedRef` to `allFiltered` — even when the active segment is `favorites` — so a `searchText` change can display non-favorite sessions under the Favorites segment. This runs alongside the mode-aware `allGrouped` computed (`SessionList.vue:293-298`) and its watcher (`SessionList.vue:301-303`). The expected behavior for this contract stays the **getter-level** contract (`favoritesFiltered`, `sessions.ts:208-224`); this is a known open UI defect and is not fixed in P01. Verification limit: reproduced with a focused Vue-reactivity harness (static/in-memory), **not** an Ionic-app runtime observation. [static, derived]
